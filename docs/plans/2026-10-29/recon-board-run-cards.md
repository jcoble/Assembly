## What the backend models today

### Task, question, event, and state shapes

- `BoardTask` has machine and task identity, creator session, project, title, summary, state, task and PR URLs, task start/end/update timestamps, and revision. It has no step list or run attempt. Verified: `dotnet/Assembly.Application/Features/Workflows/Contracts/BoardTask.cs:3-4`.
- Valid task states are `queued`, `running`, `paused`, `waiting`, `completed`, `failed`, and `cancelled`. Completed, failed, and cancelled are terminal for task duration. Verified: `WorkflowTransitions.cs:12-14`.
- `BoardQuestion` stores key, generation, kind, prompt, recommendation, asked/answered times, answer, delivery identity/state, and accepted revision. Its database kind check permits only `text` and `approval`. Verified: `Contracts/BoardQuestion.cs:3-4`; `WorkflowSchema.cs:44-50`.
- `BoardAnswerValue` is a string kind plus optional text. The transition accepts `text`, `approve`, or `deny`; text questions take text, approval questions take approve or deny. Verified: `Contracts/BoardAnswerValue.cs:3-4`; `WorkflowTransitions.cs:118-141`.
- Answer delivery states include `pending`, `delivered`, `delivery_failed`, `delivery_unknown`, and `recorded_in_chat`. An answer is persisted before delivery; uncertain delivery is not automatically resent. Verified: `WorkflowTransitions.cs:104-115, 127-141, 158-185`; `BoardTools.cs:44-67`.
- `BoardEvent` records a sequence, task key, event kind and timestamp, full task snapshot, zero or one question snapshot, and optional changed paths. There is no typed step or action field. Verified: `Contracts/BoardEvent.cs:3-4`; `WorkflowTransitions.cs:210-219`.
- `BoardMetrics` has nullable done/failed/skipped step counts, file count, and tool count. The page and task SQL currently set the step and tool metrics to null; file count is computed from changed paths. Verified: `Contracts/BoardMetrics.cs:3-4`; `WorkflowQueries.cs:64-71, 101-106`.
- Storage is `board_tasks`, `board_questions`, and `board_events`; no step table exists. `board_events.payload_json` stores the event snapshot. Verified: `WorkflowSchema.cs:38-60`.

### Updates, reads, writes, and topics

- `WorkflowTransitions.Update` creates or updates one task, writes a `task_reported` event by default, and can also record one question or one answer received in chat. Identical progress is a no-op; changing state updates `EndedAt` for terminal states and clears it for nonterminal states. Verified: `WorkflowTransitions.cs:21-34, 39-53, 67-100`.
- `WorkflowTransitions.Commit` writes the task, question if present, and event in one writer transaction. It then publishes a `board` invalidation keyed by machine and task, carrying revision and sequence. Verified: `WorkflowTransitions.cs:210-219, 241-249`; `Contracts/BoardChange.cs:3-4`.
- `board/page` reads `BoardPageArgs(project, state, cursor)` and returns task summaries, counts, continuation cursor, and event watermarks. It pages 40 at a time. Unanswered questions sort first, then live tasks, then terminal tasks. Verified: `WorkflowCalls.cs:14-20`; `Contracts/BoardPageArgs.cs:3-4`; `Contracts/BoardPageResult.cs:3-4`; `WorkflowQueries.cs:62-87`.
- `board/task` reads `BoardTaskArgs(machineId, taskKey, beforeSeq, questionCursor)` and returns the task, questions, feed, metrics, and independent event/question cursors. Verified: `WorkflowCalls.cs:21-25`; `Contracts/BoardTaskArgs.cs:3-4`; `Contracts/BoardTaskResult.cs:3-4`; `WorkflowQueries.cs:25-35, 90-110`.
- `board/answer` writes `BoardAnswerArgs(machineId, taskKey, questionKey, generation, answerKey, answer)` and returns an acceptance record. It routes to local or mirrored remote source. Verified: `WorkflowCalls.cs:26-34`; `Contracts/BoardAnswerArgs.cs:3-4`; `Contracts/BoardAnswerResult.cs:3-4`.
- `board/changes` reads local event changes after a sequence number. The desktop page does not call it directly; `RemoteWorkflowMirror` calls it to catch up a remote Board after subscribing to that machine's `board` topic. Verified: `WorkflowCalls.cs:19-20`; `RemoteWorkflowMirror.cs:63-68, 138-152`.
- `RemoteWorkflowMirror` subscribes to the remote `board` topic, replays committed events, and routes task detail and answers to the configured remote source. New event fields must be added to the shared contract and both JSON contexts. Verified: `RemoteWorkflowMirror.cs:14-19, 63-68, 145-170, 173-179`; `WorkflowSchema.cs:7-32`; `WorkflowJson.cs:5-29`.

### MCP reporting tool

- The only Board MCP tool is `board_update`. `tools/list` publishes it, and `tools/call` routes that name to `BoardTools`. Verified: `McpRoutes.cs:63-80`; `BoardTools.cs:70-91`.
- A non-helper session can report only its own local task. Helpers are refused, and remote sessions cannot report through this tool. Verified: `BoardTools.cs:18-24`.
- `board_update` requires task key, title, state, summary, task URL, PR URL, changed paths, question, and answer receipt fields; nullable values must still be present. Verified: `BoardTools.cs:102-110`.
- Its question payload supports only text or approval questions, with prompt and optional recommendation. Its answer receipt supports text, approve, or deny. Verified: `BoardTools.cs:111-121`.
- There is no MCP step-posting tool. An agent reports state and summary, changed paths, and optional question/answer through `board_update`; there is no per-step percentage, elapsed time, attempt, or run-action field. Verified: `BoardTools.cs:74-76, 102-121`; `Contracts/BoardUpdateArgs.cs:3-4`.
