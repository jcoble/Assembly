## C. What moving the link onto /socket changes
Assumes the C2 shape in recon-cut-c2.md: remote registers the existing features (ServeRun.cs:51) plus the missing outbox and version calls; desktop opens one `/socket` per remote.

1. **Deploy script (`workbox.sh`)**: no change needed. It already publishes `Assembly.Remote` and restarts the unit (:108,121); the new features ride in the same binary. `serve` mode still "ready" means `is-active` (:123) only; it doesn't check the socket. (Optional, not required: nothing.) verified/assumed
2. **Unit**: no change. Same `ExecStart` (:118), same flags, same port. Only the code behind `/socket` grows. The unit has no `Restart=`, so a crashed host stays down; that is true today and not changed by C2 (assumed no new requirement). verified
3. **Tunnel**: one forwarded port is still enough. `ssh -L` forwards raw TCP (RemoteTunnel.cs:59); a WebSocket upgrade on `/socket` goes over the same `127.0.0.1:{BOX_PORT+10000}` as HTTP and `/live` do today. The tunnel code needs no change; `RemoteConfig.Address` (`http://127.0.0.1:{localPort}`, RemoteTunnel.cs:76) is turned to `ws://.../socket` by the client the way `RemoteFollower` does for `/live` (`RemoteFollower.cs:85`). Reachability: one socket open/closed replaces the probe (plan :1535-1537 per the route map); a dead ssh already restarts with backoff (:121-157). verified (TCP forward) / assumed (client URL change)
4. **Token handling**: same token, same file, same ssh read (RemoteTunnel.cs:89-100). It moves from the `Authorization` header (RemoteMachine.cs:41, RemoteFollower.cs:84) to the `hello` frame (`SocketConnection.cs:129-150`). `/socket` skips the header guard (TokenGuard ~:39), so the guard itself doesn't change. The token stays in memory and out of argv/URL (better than `/live?token=`, which used the query). verified
5. **check4 `/version` (:71-72) and `GET /sessions/{id}` (:135)** on the box base: both are HTTP routes planned for removal (route map rows 1 and 5). To keep them, check4 must use the socket: (a) a `/version`-equivalent: the host needs a socket read returning `commit` (and `formatVersion` for `RemoteMachine.CheckFormatAsync`, `RemoteMachine.cs:184`); the welcome frame has only `protocol` and `machine` (`SocketConnection.cs:150`), so either add `commit`/`formatVersion` to it or add a call; (b) the session's `acpSessionId`: the `sessions` topic item has no `acpSessionId`? It does (`SessionItem.cs:6-7` lists sessionId, agent, repoUrl, title, machine, parentSessionId, acpSessionId, updatedAt), so a `sessions` get by key works on the box once the remote registers the feature (`SessionsFeature.cs:33-34`); check4 would need a small node script like `socket.ts` (bash+curl can't speak the socket). Alternative for (b) with no change: read `acpSessionId` from the LOCAL backend's copy, since the desktop already stores the session with `machine` set (assumed, not checked whether the local row has `acpSessionId` for remote sessions). The box token and the box base stay the same. verified (lines) / assumed (alternatives)
6. **Scenario `socket.ts`**: unchanged in shape. Once the remote registers features, the `check4/nothing` call still answers `not_found` (:36-40) because no feature `check4` exists. verified/assumed
7. **Evidence scripts**: `check-evidence.sh` and the summary layout don't change. `builtFrom.workboxTest` keeps coming from the box commit (:72, :168), so whatever replaces `/version` must still give a commit. `row-log.ts` (dotnet/scripts) uses `/sessions`, `/rows` pages and `/live` over HTTP on the box (:38,:71): these go away with the routes, so it needs the socket form or a deletion; it runs on the box against `127.0.0.1:port` directly, no tunnel. verified (calls) / assumed (needs update)
8. **Old hosts that must not be touched (9797 assembly-dotnet, assembly-remote, tanstack-relay, tanstack-agent-server)**: C2 changes nothing on them by itself; the deploy script only acts on this checkout's `$BOX_UNIT`/port/data (`workbox.sh:80-124`), and main's unit is guarded to clean origin/main (:66-75). Lanes use `9797+10n` ports (`lane-env.sh:21`), so a lane's host never collides with 9797. Risk: the lane's desktop (new, socket-only) cannot talk to an OLD host on 9797 that registers no features and has no outbox/version calls (a main host still on the old HTTP build); and an old desktop talking to a new host works only as long as the HTTP routes stay on the host until the cut. So: do NOT redeploy main's unit (needs the guard's clean main anyway), deploy only lane units, and keep the HTTP routes on the host until every desktop is on the socket (assumed; matches the route map's delete order, recon-cut-c2.md §4). The unit-name reserve for other services: the script says "touches nothing the tanstack-agent-server and tanstack-relay services use" (`workbox.sh:20`); verified for the script, not checked on the box (read-only rule). verified/assumed
