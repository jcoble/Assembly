Extension integration review

Use the ecosystem without rebuilding VS Code.

Mac Command Bar already contains the difficult foundation: one Monaco/VS Code compatibility runtime, an extension-host worker, real file models, and trusted Rust services. The next move is a curated extension layer—not a second editor architecture.

REPOSITORY REVIEW
2026-08-03
Recommendation Install full extensions only when they are declarative or explicitly browser-compatible. For Git, files, processes, and workspace state, expose the app's existing Rust services through a small VS Code-compatible provider rather than allowing another extension to run a competing backend.

The app is already halfway there

This is not plain Monaco. The current dependency and worker setup is specifically designed to run VS Code services and selected extensions.

01

One VS Code-compatible runtime

csharpLanguageClient.ts imports the local extension host and starts one global MonacoVscodeApiWrapper. New extensions must attach to it, never initialize another copy.

02

Extension worker already wired

monacoWorkers.ts routes the extension-host worker. That makes curated local web extensions realistic without introducing a Node process.

03

Trusted native services exist

Rust already owns Git, file access, Roslyn lifecycle, validation, and session/workspace boundaries. Extensions should consume these services rather than duplicate them.

Which integration method fits each feature?

“Use an extension” is not one technical choice. The safe method depends on whether the package is declarative, browser-compatible, or depends on desktop Node APIs.

Minimal-disruption architecture

One runtime, one workspace identity, one native authority. Extensions add commands and UI contributions; they do not become a parallel application.

Add beside the editor

  • src/lib/shell/extensions/extensionRuntime.ts — attaches registrations to the existing singleton runtime.
  • extensionCatalog.ts — explicit allowlist, kind, license, and enable state.
  • extensionWorkspace.ts — maps the active session's workspace into the extension API.
  • MonacoDiffEditor.svelte — isolated native diff surface.

Do not add to the giant components

  • Do not put extension management into the roughly 2,900-line MonacoSourceEditor.svelte.
  • Do not put more Git integration into the multi-thousand-line Rust main.rs; extract a git module when that bridge changes.
  • Do not let a third-party extension spawn Git or Roslyn beside the existing Rust processes.
  • Do not initialize the compatibility layer on every session/workspace switch.

Git, graph, and diff: use the APIs we already own

The app already has native Git commands for status, history, diff, stage, unstage, commit, fetch, pull, and push. That is more valuable than replacing the backend with an extension.

SCM

Expose Rust Git as a VS Code provider

An internal extension calls vscode.scm.createSourceControl, translates existing stores into resource groups, and forwards actions to Tauri commands. One source of truth, standard extension-facing API.

DIFF

Use original and modified models

The current custom diff component parses unified text. Native DiffEditor needs the base file plus the current file; Rust can provide both safely for the selected workspace and revision.

GRAPH

Keep the current data path

Continue using the existing Rust history model and graph lanes. A later rendering library may replace only the visual layer, but neither GitLens nor Git Graph should become the repository authority.

Recommended sequence

Each phase has an explicit stop condition so an experiment cannot quietly turn into a second IDE platform.

PHASE A

Exact Houston theme + native diff

Register the official theme colors through the existing theme service; keep app, Monaco, and terminal colors coordinated. Replace text-only diff for normal files with DiffEditor.

Stop condition: theme survives editor/session switching, and working-tree plus committed diffs render from real models.
1–3 days
PHASE B

Curated extension runtime

Add the allowlisted catalog, registration lifecycle, active-workspace adapter, and one harmless declarative or browser extension as the packaging proof.

Stop condition: exactly one runtime and one registration per extension across repeated switching among five workspaces.
2–4 days
PHASE C

Internal SCM provider

Project existing Rust Git state and commands into VS Code's SCM API. Keep current panels while adding standard commands and interoperability.

Stop condition: no duplicate Git subprocess, no cross-session repository state, and existing Git workflows remain intact.
2–4 days
PHASE D

GitLens browser compatibility spike

Load it only in a disposable feature flag and inventory missing services. Use the spike to learn which reusable views or commands are attainable—not to commit to the extension.

Stop within four hours if it cannot consume the existing repository provider without a Node/remote extension host; do not add that host during the spike.
1–2 days max

Full-extension admission gate

Required before bundling

  1. The manifest has a browser entry, or all needed contributions are declarative.
  2. It does not require direct Node fs, child_process, sockets, or a local executable.
  3. The current runtime has every required VS Code service/view API.
  4. The license permits bundling and distribution in this app.
  5. It remains isolated while switching among several session workspaces.

Implementation guardrails

  1. Extensions are allowlisted and pinned—not installed from arbitrary marketplace URLs.
  2. Filesystem and process access always crosses validated Rust commands.
  3. Extension startup never blocks Monaco mounting or the conversation surface.
  4. Failures disable the extension, not the editor.
  5. Native Tauri behavior—not a browser-only preview—is the acceptance target.
