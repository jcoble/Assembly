Why the prototype’s CodeLens works and Mac Command Bar’s does not

The working prototype gives Roslyn a real VS Code-compatible CodeLens client. Mac Command Bar starts the same Roslyn server, but replaces its CodeLens protocol with a handcrafted symbol-and-reference counter. That substitution is the primary defect; the current dirty tree also disconnects the handcrafted fallback entirely.

Review complete Branch: tsk-799-code-intelligence Runtime/source edits during review: none Artifact created: this report only

Decisive finding

Mac Command Bar is not running Roslyn CodeLens.

It runs Roslyn as a backend for manual documentSymbol and per-symbol references requests. Its client advertises no CodeLens capability, sends no textDocument/codeLens or codeLens/resolve requests, and ignores workspace/codeLens/refresh. The prototype does all three through the standard language-client stack.

Side-by-side data flow

The two implementations are not equivalent

The server executable matches. The client contract and request lifecycle do not.

Working prototype

Roslyn owns the CodeLens result; the editor owns scheduling and rendering.

1. Tauri starts an authenticated loopback WebSocket and Roslyn.
2. The VS Code-compatible API boots a trusted workspace, file service, and real file:// document.
3. monaco-languageclient advertises CodeLens and refresh capabilities during initialize.
4. Roslyn advertises codeLensProvider; the client registers it automatically.
5. The client sends textDocument/codeLens, lazily resolves visible rows, cancels stale work, and accepts server refresh.
6. Roslyn supplies the title and command; standard VS Code commands open Peek.

Mac Command Bar today

The application tries to reproduce CodeLens above a manual LSP request router.

1. Tauri starts Roslyn and talks JSON-RPC over stdio.
2. The handwritten client initializes without CodeLens or refresh capabilities.
3. Monaco’s custom provider asks documentSymbol for as many as 120 anchors.
4. It eagerly asks textDocument/references once per symbol, four at a time, with 2s / 6s / 12s retries.
5. Application code deduplicates locations, removes the declaration, caps results, caches counts, and fires repaint timers.
Current dirty tree: the count callback is absent, so this path stops before reference rows are created.

What directly causes the observed behavior

Priority Finding Prototype evidence Mac Command Bar evidence User-visible result
P0 The native CodeLens protocol is absent

Changing the server binary did not connect Roslyn’s CodeLens feature to Monaco.

Pinned VS Code API, C# extension, monaco-languageclient, and vscode-ws-jsonrpc. The client advertises CodeLens + refresh support and registers Roslyn’s provider.

Only stock monaco-editor is installed. The capabilities object has no CodeLens entry. Repository source contains none of textDocument/codeLens, codeLens/resolve, or workspace/codeLens/refresh.

Roslyn can answer references, hover, and definitions while no native reference CodeLens exists.

P0 The remaining custom reference provider is disconnected

This explains the immediate “nothing appears ever” state.

Not applicable: the prototype does not need the page callback.

handleEditorReferenceCountLookup still exists, but editorMonacoCallbacks no longer passes it. The provider explicitly returns only Build/Test lenses when the callback is absent. HEAD still contains the callback, proving this is dirty WIP rather than the committed baseline.

No reference CodeLens row—neither a placeholder nor a resolved count—can render.

P0 The custom path amplifies one file into many expensive requests

It reconstructs CodeLens from reference lookups instead of consuming Roslyn’s CodeLens response.

One standard provider lifecycle obtains lenses; VS Code’s controller debounces, cancels stale requests, caches the model, and resolves only rows that need resolution.

One documentSymbol request is followed by up to 120 independent references requests, limited to four concurrent requests and retried after 2, 6, and 12 seconds. Every row is scheduled, not just the viewport.

Cold files fill slowly, compete with Peek/navigation, consume more CPU, and improve only after custom caches warm.

P1 “Initialized” is treated as “solution ready”

Protocol readiness and Roslyn indexing readiness are different states.

Provider requests, cancellation, unresolved rows, and server refresh govern the lifecycle. The editor does not invent a separate count-ready state.

Rust reports LanguageServerState::Ready immediately after initialized. The custom scheduler releases held count requests from that state even while Roslyn is still loading the solution.

Early requests are cancelled, retried, repainted, or superseded, producing late and unstable cold-start rows.

P1 The verification proved the fallback, not native CodeLens

The tests could pass while the desktop integration remained architecturally wrong.

The prototype was exercised as the real Tauri desktop against the 1,568-file EdiPlatform workspace.

The integration document says browser Playwright exercised the fallback counter; native coverage was Rust/static. It also explicitly declares that no monaco-languageclient or WebSocket bridge is needed.

Green tests did not prove the path the user actually runs on macOS.

Exact correction boundary

Copy the client contract, keep the useful native shell

Do not run the prototype and custom counter side-by-side. Native C# must have one CodeLens authority.

Copy from the prototype

  1. The exact pinned VS Code-compatible Monaco dependency family.
  2. Trusted workspace + real file:// URI + filesystem overlay boot order.
  3. LanguageClientWrapper over an authenticated, transparent WebSocket bridge.
  4. Standard CodeLens capability, provide, resolve, cancellation, cache, and refresh lifecycle.
  5. Standard VS Code reference-provider and Peek commands.

Keep from Mac Command Bar

  1. The official Roslyn executable discovery and packaging.
  2. Canonical-root identity and bounded five-workspace LRU pool.
  3. Project/session activation warming before a file opens.
  4. Owned process groups and child cleanup.
  5. Rust-backed Build/Test actions, Git, terminal, and workbench features.

Disable for native C#

  1. The custom reference-count CodeLens provider.
  2. documentSymbol as a replacement for Roslyn CodeLens anchors.
  3. Per-symbol eager references counting and retry timers.
  4. Application-owned count title, declaration subtraction, and repaint state.
  5. Any synthetic cold-start 0 references value.

Important adaptation

Do not copy the prototype’s “one Roslyn process per WebSocket” limitation. Expose a WebSocket session backed by Mac Command Bar’s existing canonical-root Roslyn pool so each workspace still owns one server. The bridge must transparently carry every JSON-RPC message instead of interpreting a hand-selected method list.

Definition of done

Five checks that prove parity

These checks target the real Tauri desktop, not the browser fallback.

  1. Protocol: capture a native trace showing textDocument/codeLens, codeLens/resolve, and support for workspace/codeLens/refresh.
  2. Cold start: activate a C# session before opening the editor; verify Roslyn starts, and opening a file never paints a fabricated 0 or intermediate count.
  3. Correctness: compare final titles on fixed symbols against the known-working prototype and VS Code, then click each title and verify the same Peek reference set.
  4. Warm navigation: switch files, top tabs, sessions, and two projects; returning to a warm root keeps stable rows and does not trigger a full recount.
  5. Resources: verify one Roslyn process group per warm root, no duplicate client, no orphaned BuildHost processes, and no custom C# reference-count calls.
