Assembly conversation: memory, markdown conversion, and TSK-928

Branch tsk-808-assembly-wave · written 2026-08-29 · every claim below carries a file:line receipt verified against the working tree

The goal, in the owner's words: the chat "can take up some mem, but not make it rise steadily and not be able to be gc'd." The app is deliberately stripped down and subsystems are being reconnected one at a time to find what costs memory. Chat is one of the big ones.

01 · What is actually wrong

Four findings, all verified by reading the code. They are independent, and the first two are the ones that make memory climb.

Finding 1 — the whole transcript lives in a deep $state

conversationStore.svelte.ts:166

export const conversationSessions = $state<Record<string, ConversationWorkspaceState>>({});

This is the only $state in the file and it is deep. Everything reachable from it is proxied: loadedEvents, timeline, agentItems, childTimeline, recentEvents, plus roughly a dozen Record<> fields — about 60 fields per session.

In Svelte 5 every nested object becomes a Proxy with a signal per touched property, and arrays additionally carry version signals. So appending one streamed delta does not just add an event object; it materialises proxies and signals for that object and its payload, all strongly reachable from a module-level root. They are not garbage — they are live reactive state, and nothing drops them until the whole session record is evicted.

That is precisely the reported symptom: rises steadily, cannot be collected.

Finding 2 — two O(n²) re-computations per streamed token

ConversationMessage.svelte:24

const blocks = $derived(parseSafeMarkdown(text));

text is a prop that changes on every delta, so the entire message is re-tokenised through marked from scratch on every token, and the previous block tree becomes garbage. Because the list is virtualised, this also re-runs on every scroll-driven remount.

ConversationSurface.svelte:107-121

const visibleTimeline = $derived.by((): ConversationDisplayItem[] => {
  ...
  const items = typedConversationTimeline(
    conversation.agentItems,      // reads the whole array
    legacyTimeline,
    {},
    previousVisibleTimeline,
    conversation.sentAttachments
  );

Reading conversation.agentItems inside a $derived subscribes to it, so any delta invalidates the derivation and the whole transcript is re-projected per token.

Neither of these is a leak in the strict sense, but together they generate constant allocation churn that reads as steadily rising memory and keeps the collector busy.

Finding 3 — the ceiling is high, and until this wave it never fired

conversationStore.svelte.ts:84-86

The old cap was 8 MiB measured by textBytes(), which returns 0 unless import.meta.env.DEV. Shipped builds run vite build, so the cap was dead code and no trim ever ran. It is now an event count:

export const CONVERSATION_RECENT_EVENT_CAP = 200;
const ACTIVE_EVENT_WINDOW_EVENTS = 20_000;
const ACTIVE_EVENT_WINDOW_TRIM_EVENTS = 15_000;

So a working ceiling exists for the first time, but 20 000 raw events — including every assistantDelta — is a lot to hold proxied. timeline (:410) and agentItems (:639) have no cap of their own; they are bounded only indirectly, by the rebuild that runs when the event window trims.

Finding 4 — the refetch path that trimming depends on is broken

Blocks lowering the cap. prependOlderConversationEvents loses the transcript. Prepending a two-event older page onto a two-event transcript returns a timeline of one row:

expected ['Older question','Older answer','Newer question','Newer answer']
actual   ['Older question']

Reproduce with node --experimental-strip-types scripts/agentConversationStore.test.ts. It is pre-existing — the leak commit touched only the trim arithmetic in that function, not the snapshot rebuild underneath it. Trimming is only safe because trimmed rows are refetchable, so this must be fixed before the window is lowered.

03 · Phase 1 — move the transcript out of the reactive root

Phase 1

The pattern is already half-built. ConversationTimeline.svelte:621-622 already gates its work on a revision counter, not on the array:

if (timelineRevision === lastContentRevision) return;
lastContentRevision = timelineRevision;

and the store already bumps it at conversationStore.svelte.ts:362 and :621. The components do not need the transcript to be reactive; they need timelineRevision to be reactive.

Contract

  • conversationSessions stays $state and keeps the small UI fields that genuinely want per-property reactivity and do not grow: draft, sending, sendError, attachmentError, mode, scrollTop, metadata, pendingApprovals, pendingInputs, connectionState, timelineRevision.
  • Five growing arrays move to a plain module-level Map<string, ConversationTranscript> keyed by ownedId, with no proxies: loadedEvents, timeline, agentItems, childTimeline, recentEvents.
  • Mutation stays in place and O(1) per delta. Writers bump timelineRevision exactly where they do today.
  • Readers go through accessors — conversationTimeline(ownedId), conversationAgentItems(ownedId) — and re-read when timelineRevision changes.
  • evictConversationSession (conversationStore.svelte.ts:1752-1759) additionally deletes the Map entry. One reference drop then releases the whole transcript to GC.

Blast radius — only three components read those arrays

FileReads
ConversationSurface.svelte:104,119timeline, childTimeline, agentItems
ConversationHistorySurface.svelte:28-29agentItems, timeline
SourceControlPanel.svelte:153timeline.some(...)

Also fix, in the same phase

  • ConversationSurface.svelte:107 — visibleTimeline must stop re-projecting the whole transcript per token. Key the projection on timelineRevision and reuse previousVisibleTimeline, which the function already accepts for this purpose.
  • Give timeline and agentItems explicit caps, mirroring the existing event-window shape with 0.75 hysteresis. After trimming from the front, rebuild the affected index Map — timelineIndexBySession / agentItemIndexBySession at :223-224 store array positions, which every trim invalidates. Drop trimmed items from activeReasoningBySession (:225), which otherwise holds strong references to them.

Do not

  • Do not convert the arrays to $state.raw. That forbids in-place mutation, so every delta would copy the array — O(n) per token, worse than today.
  • Do not change what any counter in resourceDiagnostics means.
  • Do not change the props the 15 TSK-928 components expect. Phase 4 depends on that shape.

Verification

pnpm run check:svelte
node --experimental-strip-types scripts/agentConversationStore.test.ts

Then in the running app, with a long turn streaming: RSS rises while the turn runs, flattens when it ends, and drops when the session is switched away. Record all three numbers. Flattening is the acceptance criterion — not a particular figure.

05 · Phase 3 — markdown conversion moves to Rust

Phase 3

Today the frontend tokenises markdown in JS. conversationMessageSafety.ts:1-14 is explicit that the output is data, not markup:

The renderer deliberately returns data rather than HTML. Svelte renders every text value as text, so a partial fence or a provider supplied <script> can never become executable markup while a turn is streaming. Nothing here produces a string of markup, and nothing downstream needs a sanitizer.

That is what makes moving it to Rust safe and correct. What gets stored is a parse tree of the message's own markdown, which is as stable as the markdown itself — not a rendering, and not a view-layer decision.

The stored shape

SafeMarkdownBlock is already fully specified at conversationMessageSafety.ts:18-44 and is the wire format. Rust must produce exactly this, serialised with the same tag names:

type SafeMarkdownBlock =
  | { kind: 'paragraph'; parts: SafeInlinePart[] }
  | { kind: 'heading'; level: number; parts: SafeInlinePart[] }
  | { kind: 'code'; language: string; value: string; complete: boolean }
  | { kind: 'quote'; blocks: SafeMarkdownBlock[] }
  | { kind: 'list'; ordered: boolean; items: SafeListItem[] }
  | { kind: 'table'; headers: SafeInlinePart[][]; rows: SafeInlinePart[][][] }
  | { kind: 'rule' };

Note complete: boolean on a code block. The type already models a half-written fence, which is what makes streaming from the backend workable rather than a second path.

Decisions to hold to

Parser
comrak, not pulldown-cmark. The frontend uses marked's GFM tokenizer (marked ^18.0.10), so tables, strikethrough, task lists and autolinks must match. A parser that disagrees on edge cases silently changes how existing transcripts render.
Storage unit
The finished message, not the delta. This is where the memory win is: events currently takes one row per event (core/src/session_store.rs:433, insert at :857) and the frontend holds up to 20 000 of them. Per-message rows reduce that to hundreds.
Versioning
Add a format_version column now. SCHEMA_VERSION is 12 at core/src/session_store.rs:9 with an established user_version migration pattern. TSK-928 will add block kinds; stored rows then need re-conversion on read. Cheap to design in, expensive to retrofit.
Streaming
The backend tokenises incrementally and streams blocks over the existing channel (registerAgentConversationStream, conversationService.ts:63,774). One path, not a live path plus a stored path.
Frontend
parseSafeMarkdown and the marked dependency leave the conversation path. ConversationMessage.svelte takes blocks as a prop instead of deriving them from text, which also deletes the O(n²) in Finding 2.

Keep expectations honest. Phase 3 is mainly a CPU and bundle win. It reduces memory only through the per-message storage unit, and the block trees still land in whatever the store holds — so it complements Phase 1 rather than replacing it. Done without Phase 1, the app holds block trees instead of event objects and the curve looks the same.

Note from TSK-928 worth acting on early

An imported conversation stores a narrower record set than a live run. Confirm what is in the store before blaming the renderer:

sqlite3 <copy of sessions.db> "select json_extract(payload,'$.payload.kind') k, count(*) from events group by k"

07 · Phase 5 — the editor holds each open file several times over

Phase 5

Reported separately by the owner: the editor adds a lot of memory, "esp if you open more than one tab." Independent of the conversation work; can run at any point.

What one open tab costs today

editorStore.svelte.ts:164-165

draftContent: readOnly ? null : retainedDraft ?? preview.content,

openFiles[i].preview.contentfull textfull text
openFiles[i].draftContentsame string reference — freesecond full copy

One EditorView is created and reused across tabs (CodeMirrorSourceEditor.svelte:861), which is correct. The cost is the retained per-path EditorStates: sessionEditorStates at :149, limit retainedEditorStateLimit = 24 at :151.

Undo is not a factor — history({ minDepth: 5 }) at :651 keeps roughly five events.

Two aggravating factors, both verified

1 · Closing a dirty tab frees nothing. editorStoreOps.ts:165-169:

/** A clean closed tab can release its Monaco model; a draft cannot. */
export function modelPathToDisposeOnClose(
  file: Pick<OpenEditorFile, 'path' | 'dirty'> | null
): string | null {
  return file && !file.dirty ? file.path : null;
}

So closeFileNow (EditorPanel.svelte:1042-1046) never calls disposeTabModel for a dirty file. closeEditorFile drops it from openFiles, but the EditorState — rope, syntax tree and history — stays in sessionEditorStates until the 24-entry LRU evicts it. This is deliberate: it preserves the draft if the file is reopened. The consequence is that closing tabs does not give memory back.

2 · No file-size guard anywhere in the open path. Grepping src/lib/shell/editor/, src/lib/sourceData.ts and EditorPanel.svelte finds none. A 4 MB file becomes a 4 MB string plus a 4 MB rope plus a tree several times that, and up to 24 such states can be retained.

Measure before changing anything — it is already instrumented

resourceDiagnostics.svelte.ts:32-36 already tracks the four numbers that settle which term dominates:

codeMirrorEditorViews    // must stay 1
codeMirrorEditorStates   // retained states, ceiling 24
codeMirrorDocBytes       // the state on screen
openTabDocumentBytes     // sum across the strip

Open several tabs of known size, read these four, and compare against process RSS. Only then decide which of the fixes below is worth making.

Candidate fixes, cheapest first — pick from measurement, do not do all of them

  1. Stop holding the text twice for a dirty file. draftContent and preview.content are distinct strings once edited. The EditorState is already the authority on current text, so the store may not need draftContent at all — check every reader before removing it.
  2. Lower retainedEditorStateLimit from 24. It exists to make tab switching instant; a smaller number with the same LRU keeps that for the tabs actually in rotation.
  3. Release the syntax tree for tabs not on screen. The tree is the largest single term and is rebuilt on demand. Retaining the document and view position while dropping the parse is the best ratio available here.
  4. Add a size threshold above which a file opens without language support — no tree, no semantic features, plain text. Large files are exactly where the multiplier hurts.
  5. Give the dirty-close case a bound. Either persist the draft outside CodeMirror so the state can be disposed, or cap how many dirty closed states are retained.

Items 1 and 2 are small. Items 3 to 5 are design changes and each needs its own spec — do not start one without measurement pointing at it.

Verification

npx tsc --noEmit
pnpm run check:svelte
node --experimental-strip-types scripts/editorStore.test.ts

Then: open the same set of tabs before and after, compare the four counters and process RSS, and confirm closing every tab returns memory to roughly the pre-open baseline. That last check is the one that matters — it is what "can be gc'd" means here.

08 · Phase 6 — stored payloads are far larger than what is displayed

Phase 6

Raised by the owner: "we should cut down on things like file diffs, where it's saving the entire file. We don't need all that… Makes what's actually displayed way less as well since it goes by bytes and not what's actually displayed."

The diff builder has no hunk splitting

src-tauri/src/agent_conversation/manager.rs:5876

fn unified_diff(old_text: &str, new_text: &str) -> String {
    let old: Vec<&str> = old_text.split('\n').collect();
    let new: Vec<&str> = new_text.split('\n').collect();
    let mut prefix = 0;
    while prefix < old.len() && prefix < new.len() && old[prefix] == new[prefix] {
        prefix += 1;
    }
    let mut suffix = 0;
    while suffix < old.len() - prefix
        && suffix < new.len() - prefix
        && old[old.len() - 1 - suffix] == new[new.len() - 1 - suffix]
    {
        suffix += 1;
    }
    let removed = &old[prefix..old.len() - suffix];
    let added = &new[prefix..new.len() - suffix];

It trims one common prefix and one common suffix, then emits everything between them — every line of removed, then every line of added, as a single hunk.

Two distant edits defeat it completely. Change line 10 and line 900 of a 1000-line file: the prefix stops at line 10, the suffix stops at line 900, and the emitted patch contains lines 10-900 as - lines and again as + lines. Roughly 1,780 lines to describe a two-line change — the file stored nearly twice over, per edit event.

The input is the ACP diff content block, whose oldText / newText are whole file contents (read at manager.rs:5759-5760). So the whole file arrives, and for any non-adjacent pair of edits nearly all of it is retained.

Fix

Replace the hand-rolled function with a real line diff that splits into hunks with a small context radius. The similar crate does exactly this and is the smallest change:

TextDiff::from_lines(old_text, new_text)
    .unified_diff()
    .context_radius(3)
    .to_string()

Output stays a unified diff, so FileChangeItem.svelte's parser (:41-63, which already skips diff --git, index, +++, ---) needs no change. Verify against a fixture with two edits 800 lines apart and assert the patch is tens of lines, not thousands.

Twelve lines are displayed; the whole patch is retained

FileChangeItem.svelte:15,80-81

const DIFF_LINES_KEPT = 12;
const rows = $derived(foldable && !diffOpen ? allRows.slice(0, DIFF_LINES_KEPT) : allRows);

A collapsed file row shows twelve lines. The full diff string is held in the event payload, in loadedEvents, in agentItems, and — until Phase 1 lands — inside the deep $state proxy graph. Fixing the hunk splitting above removes most of this; a further clamp at ingest (store at most N lines, refetch the rest on expand) is only worth doing if measurement still shows diffs dominating.

The event-count ceiling is blind to payload size

A weakness introduced by the current fix, and the owner is right about it. ACTIVE_EVENT_WINDOW_EVENTS = 20_000 counts events, not bytes. One event carrying a multi-megabyte diff counts as one. So the window can hold hundreds of megabytes while the counter reads a few dozen events. The previous byte cap would have caught this — except it never ran, because textBytes() returned 0 outside dev.

The budget needs both terms: a count ceiling and a bound on any single payload. Order matters — fix the diff builder first, measure, and only then decide whether a per-payload clamp is still needed. Do not reinstate a whole-window byte measure that walks every event on every append; that cost is why the original was written to be skipped outside dev.

Verification

cd tauri-svelte-preview
MCB_RUN_CSHARP_LSP_SMOKE=0 cargo test --manifest-path src-tauri/Cargo.toml unified_diff -- --nocapture

Add a Rust unit test with two edits 800 lines apart, asserting the emitted patch line count. That is a data test, not a UI test, so it is in scope under the no-UI-regression-tests rule.

09 · Phase 7 — language servers, not yet in any measurement

Phase 7

Read this before trusting any number in this document. The owner has had the language server switched off for every measurement taken so far, and reports it "adds so much more memory." So every figure gathered to date is a floor, not a ceiling, and the phases above are ranked against a workload that excludes the largest single term.

Most of the cost is not in the JS heap

A language server is a separate process. Roslyn in particular runs to hundreds of megabytes for a real solution. That memory is process RSS and will not appear in a webview heap snapshot, in resourceDiagnostics, or in any of the counters the other phases rely on. Measuring it means sampling the server's process tree, which the Resource Manager already does through resourceSampleBackend / readResourceTotals.

Practical consequence: the conversation and editor phases should be measured with the server off, so their effect is visible. The server is measured separately, by process. Mixing them hides both.

The asymmetry worth fixing

src-tauri/src/lsp.rs:2499, :2520, :2589, :3162

The stop paths are explicit and well built — stop_all_servers, stop_servers_for_language, stop_servers_for_root, and stop_lsp_process_tree kills the whole process group rather than orphaning children (:3162-3172), which is the same hygiene the ACP sidecars use.

What is missing is a quiescence rule. Servers are keyed per root and language (preload_languages_by_root, :1676), so several can run at once, and the stop paths found are all explicit — triggered by a root change, a language change, or shutdown. Nothing observed stops a server that has simply gone idle.

Compare the project's own rule for ACP runtimes: once a turn and all its related work are quiescent, suspend_if_quiescent detaches the session and stops the sidecar process group when its pool has no other members. Language servers have no equivalent. A server started for a project the reader has stopped looking at stays resident with its full index.

Investigate before designing

  1. Confirm the gap. Search lsp.rs for any idle timer or activity-driven stop; LanguageServerActivity (:428) already tracks activity per key and may be the hook a quiescence rule would hang from. Do not assume it is absent because this pass did not find it.
  2. Measure per server: RSS of each language-server process tree, with one project open and then several, idle and during a burst of edits. Distinguish steady-state index size from working set during a parse.
  3. Count concurrent servers in a realistic session. Servers × roots × languages is the multiplier that matters.

Likely shape of the fix, if the gap is confirmed

  • Stop a server whose root has had no open file and no request for some interval, reusing the existing stop_servers_for_root path. The next request restarts it, exactly as a suspended ACP session resumes.
  • Cap how many servers may run at once, evicting least-recently-used by root.
  • Do not preload a language until a file of that language is actually opened, if preload_languages_by_root currently does otherwise.

Each of these is a lifecycle change to a subsystem the owner depends on. None should be written without the measurements above — a server stopped too eagerly turns every file open into a cold start, which is the failure mode this app exists to avoid.

10 · Open question, not yet diagnosed

Row spacing in the transcript was widened on 2026-08-29 — .turn-row gap 16px → 22px (ConversationTimeline.svelte:821), work-row pull −8px → −6px and user margin 12px → 16px (TimelineItem.svelte:86-87).

If the reported symptom was rows overlapping rather than merely tight, that is a virtualisation measurement bug and the spacing change only masks it. Rows are absolutely positioned at transform:translateY(row.start) with heights from measureElement (:679); any row whose real height exceeds its measured height pushes every row below it too high. Unmeasured rows fall back to ROW_MIN_HEIGHT = 44 (:138,:166), far short of a real message. Needs eyes on the running app before anyone changes the measurement path.

11 · Rules every lane on this work carries

  • KISS. The smallest diff that makes the named behaviour work. If two designs work, ship the one with fewer moving parts.
  • YAGNI. No code for hypothetical futures. A new interface, config flag, compatibility shim, factory around one call site, drive-by refactor, or speculative caching layer that this spec did not ask for is a defect, not a bonus.
  • One way only. A change is finished when the old path is deleted. No legacy fallback kept "just in case", no feature flag keeping both alive.
  • No new UI regression tests. Nothing asserting on component structure, layout, panels, menus, styling or colour. Tests for logic and data are still expected.
  • No CSS :has(), and no Tailwind has-[…]. Banned repo-wide.
  • Performance is the product. Anything animated or periodic must prove it does not add idle cost: near-0% CPU at rest over ~10s, document.getAnimations().length at rest, click-to-interactive under ~350ms.
  • Architecture page. Any commit changing what main-architecture-explained.html describes updates it in the same commit and adds a change-log row; otherwise the message carries Architecture: unchanged. Enforced by .githooks/commit-msg.
  • Commits end with Committed-by: <name>. Never a co-author trailer.
  • Exceeding roughly twice the stated diff size, or needing a file this spec did not name, means stop and send back a one-paragraph proposal.

12 · Order of work

  1. Phase 1 and Phase 2 in parallel — different files, no overlap.
  2. Measure. If RSS still climbs after Phase 1, the culprit is outside the conversation store and the next step is a heap snapshot, not more refactoring.
  3. Lower ACTIVE_EVENT_WINDOW_EVENTS once Phase 2 is green.
  4. Phase 3, then Phase 4.
  5. Phase 5 is independent of all of the above and can be measured at any time; it needs its counters read before any code changes.
  6. Phase 6 is a small, self-contained Rust fix and can go at any time. Doing it early makes every later measurement cleaner, because diff payloads stop distorting the event window.
  7. Phase 7 has not been measured at all. Turn the language server on, measure by process, and re-rank everything above against that number before committing to an order.
